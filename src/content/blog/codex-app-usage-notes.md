先直说，不绕弯子

Codex App 的功能确实很前沿。它能直接读项目、改代码、开浏览器、跑测试、控制桌面应用，还能调用子代理处理任务。放在几年前，这些东西多少有点科幻。

但是，作为 OpenAI 这种大厂推出的官方编程工具，它现在还是有点拉跨

Bug 满天飞、性能优化不怎么样、偶尔会出现反人类的交互设计，还有一些很奇怪的门控小巧思。最近越来越多 ChatGPT 相关能力也在往同一个产品壳里塞，我能理解他们想把功能做完整，但实际使用起来的体感就是越来越臃肿。有时候新功能还没来得及高兴，先得研究为什么我的按钮不见了、权限被挡了，或者同一个能力为什么在另一个入口里才能用。

当然，我一边骂还是一边在用

因为只看“能帮我把项目做到什么程度”，Codex App 目前确实很强。只是想把它用得舒服一点，不能完全顺着客户端的默认设计走。下面这些经验不是官方标准答案，而是我在长时间会话、多任务项目和几次上下文事故以后慢慢留下来的习惯。

本文记录的是我在 **2026 年 7 月 27 日** 所使用版本中的体验。Codex App 更新很快，具体按钮、门控和内部文件格式以后都可能变化。

## 先给线程找个正经工作目录

如果一个线程只是临时问两句话，默认目录倒也无所谓

但只要这个线程准备长期使用，或者需要生成代码、图片、文档、测试产物，我都建议先创建一个单独文件夹，再把它设为自定义工作目录。

不要什么都让它往类似下面这种默认位置里拉：

```text
C:\Users\你的用户名\Documents\Codex
```

刚开始看不出问题。等你积累了一堆项目副本、临时素材、预览产物、依赖目录和不知道属于哪个会话的文件，再碰上一次清理 C 盘，你就可以慢慢享受了。

我的习惯是一个长期项目对应一个明确目录，例如：

```text
D:\Projects\个人博客
D:\Projects\AstrBot插件
D:\Writing\论文项目
```

目录名字不重要，重要的是人能看懂、能备份、能进 Git，也知道删东西时自己删的是什么

工作目录还会影响 Codex 能看到哪些文件、命令默认在哪里执行，以及项目里的 `AGENTS.md` 会不会生效。线程从一开始就站对地方，后面能省下很多解释。

## 一个线程最好只聊一类事情

不要在同一个线程里上午写论文，下午改博客，晚上再让它帮你写情书

GPT 的抗干扰和长上下文能力已经很强了，但上下文被不同任务反复污染以后，它也遭不住。前一个任务的术语、格式要求、代码路径和语气偏好，都有可能在后面的回答里偷偷冒出来。

最简单的判断方式是：这些内容是否共享同一批文件、同一套背景和同一个最终目标？

如果答案是否定的，就新开线程

同一个项目内部可以继续聊。例如博客的首页、文章页、播放器和部署，本来就会互相影响，放在一个长期线程里有价值。但论文和博客即使都需要写 Markdown，也没有必要硬塞在一起。

线程不是越长越厉害。能持续继承有效背景才有意义，只继承噪声就不是什么优点了

## 把长期习惯写进 AGENTS.md 和开发笔记

一个长期任务不能只靠聊天记录维持。聊到几百轮以后，哪些文件不能碰、哪个方案已经试过、当前分支有没有推送，这些东西全靠模型从历史里猜，迟早会出事。

所以我后来把自己的长期规则和开发笔记方案整理成了一个叫 `codex-development-guidelines` 的仓库，链接放在这一节最后。仓库里也有首次采用、版本更新和规则访谈等辅助文件，不过那些只服务于安装与维护。真正装好以后会长期参与工作的，主要是下面四个文件：

- 按个人环境调整后放进项目或用户目录的 `AGENTS.md`
- 决定何时维护开发笔记、维护时做什么的 `maintain-development-notes/SKILL.md`。
- 告诉 Agent 一份开发笔记可以包含哪些部分的 `references/note-schema.md`。
- 让 Codex 识别并自动调用这个 Skill 的 `agents/openai.yaml`

这四个文件并不是同一件事换了四种写法。`AGENTS.md` 管日常行为，Skill 管开发笔记的生命周期，Schema 管笔记长什么样，YAML 则负责把 Skill 接入 Codex。下面直接按照仓库里的实际内容逐条说。

### AGENTS.md：先把 Agent 的日常行为管住

参考文件里目前有 27 条规则。我不建议原样照抄，但每一条都对应一个真实问题

#### 环境与终端

- **第 1 条：说明默认环境** 我的规则以中国大陆网络、Windows、PowerShell 或 Git Bash 为基线，避免 Agent 每次都按 Linux 和国外网络环境想当然。
- **第 2 条：执行前先认清 Shell** 当前终端是 PowerShell，就使用 PowerShell 的语法；换成 Git Bash，也不能反过来往里面塞 PowerShell 命令。
- **第 3 条：命令失败后不准原样重试** 先看失败原因，再换成当前 Shell 真正支持的等价命令。连续三次执行同一个错误命令不叫坚持，叫浪费时间。
- **第 4 条：明确列出 PowerShell 不能直接使用的 Bash 写法** 像 `sed`、`awk`、`rm -rf`、`touch`、`export` 和 Here Document 都写出来，省得 Agent 明知是 Windows 还凭习惯输出一整段 Bash。
- **第 5 条：网络问题只允许临时处理** 大陆网络下载失败时可以临时指定镜像或代理，但不能为了装一个包，顺手把全局 npm、pip、Git 配置全改了。
- **第 6 条：工具不足时先说明，再询问安装** 如果现有 Shell、依赖或工具已经明显妨碍任务，就把阻碍、推荐工具、版本、来源、安装范围和影响说清楚。用户同意后也只装完成当前任务需要的最小部分。
- **第 7 条：路径统一加引号** 中文、空格和括号路径在 Windows 上太常见了，少一对引号就可能让一条本来正确的命令直接跑偏。

#### 编码与文件安全

- **第 8 条：乱码不等于文件损坏** 中文文件可能是 UTF-8、GBK 或 CP936，没确认编码前不能擅自转码、重写或格式化。
- **第 9 条：新文件和旧文件分开处理** 新建文本默认 UTF-8 without BOM；修改旧文件则优先保持它原来的编码、换行和结构。
- **第 10 条：偏好 ASCII 不等于清理中文** 命令和标识符可以尽量用 ASCII，但不能借这个理由删除、替换或转义项目里本来就存在的中文。
- **第 11 条：修改范围必须收住** 用户让我修一个按钮，就不要顺手重构半个项目，更不能把不相关内容当作“顺便优化”删掉。
- **第 12 条：高风险和主观操作先问** 删除、覆盖、批量修改、批量转码、全局配置、来源不明的图片和主观视觉判断，都不能替用户拍板。
- **第 13 条：UI 与图片判断要保守** 分不清哪张是新素材、哪张是临时图时就停下来确认，不要把猜中的第一张直接当最终版本。

#### 沟通与上下文保护

- **第 14 条：固定默认语言与回复风格** 我的项目默认中文回复，说明原因时尽量简洁，并给出能实际执行的下一步。
- **第 15 条：主线程只保留高价值信息** 长日志、完整报错栈、候选路径和大段搜索结果交给工具或子代理消化，主线程只收结论、证据、文件位置、风险和建议动作。

这条对长会话尤其重要。模型不是只会被“聊天内容”占上下文，工具返回的图片、日志和文件全文同样会把线程越撑越大。

#### 子代理使用

- **第 16 条：子代理负责脏活累活** 搜索资料、扫目录、读长文件、整理报错和比较方案都可以交出去，但结果必须压缩成摘要，不能把原始噪声再倒回主线程。
- **第 17 条：一次只给一个明确的小任务** 输入是什么、要返回什么、做到哪里停止都要说清楚，探索型子代理默认只读，也不允许自己扩张任务范围。
- **第 18 条：限制层级和并发** 默认只让主 Agent 派发一级子代理，通常同时两到四个已经足够，做完就关闭，不能无限往下套娃。
- **第 19 条：结果回来以后要收束** 主 Agent 需要整理出结论、证据、文件或行号、风险和建议，确认用完后关闭子代理，不让后台残留一排任务。
- **第 20 条：模型和推理强度分级使用** 查路径没必要上最高推理；架构、安全、复杂逻辑和疑难 Bug 才值得使用更强模型或更高 reasoning effort。

#### 写入与资源保护

- **第 21 条：最终写入权要集中** 探索代理尽量只读，真正改文件由主 Agent 或一个明确的 Worker 负责，避免几个人同时改同一片代码。
- **第 22 条：Cargo 默认限制到 `-j 2`** 这是按我的机器和使用习惯写的资源规则。不是 Rust 项目可以删掉，机器更强也可以改，但不要把参考值伪装成所有人的标准答案。
- **第 23 条：重型任务不能并行乱跑** 构建、测试、依赖安装和代码索引一次只跑一个，执行前先提醒用户它可能明显占用资源。
- **第 24 条：能复用的缓存不要重复造** 已有且版本兼容的 `node_modules`、Cargo target 和工具缓存可以复用，但复用前要确认版本，也不能覆盖用户现有目录。
- **第 25 条：长命令结束后检查残留进程** 命令窗口显示完成，不代表它启动的开发服务器、Watcher 或后台 Agent 一定退出了。
- **第 26 条：用户已经说电脑卡，就立刻停手** 先检查 CPU、内存、磁盘和残留进程，再缩小验证范围，不能继续拿“再完整构建一次”给机器补刀。
- **第 27 条：复杂任务自动考虑开发笔记** 多功能、多分支、多工作树、频繁切换、长期调查或安装回滚时，调用 `maintain-development-notes` 判断是否记录；简单任务不要为了形式建笔记。

这 27 条负责的是“Agent 平时怎么做事”。最后一条只负责把开发笔记 Skill 叫起来，至于到底要不要记、记在哪里、写什么，则由下面的 Skill 决定。

### SKILL.md：决定什么时候记、怎么维护

`maintain-development-notes/SKILL.md` 不是一份固定模板，而是一套判断流程。

- **复杂度门槛** 用户明确要求交接记录、任务跨多个线程或仓库、涉及安装回滚，或者马上要离开一个未完成的大任务时，直接维护笔记。普通情况则至少要同时出现两项复杂信号，例如多个工作流并存、反复切换任务、依赖精确提交号、存在多个失败方案，或者长到上下文压缩可能丢状态。一次性问题和简单单文件修改明确不记。
- **创建前先找旧笔记** Agent 要先搜索 `DEVELOPMENT_NOTES.md`、`DEV_NOTES.md`、`HANDOFF.md` 等已有记录，判断哪份才是权威来源，不能每换一个会话就新建一本自己的笔记。
- **选择笔记结构** 单仓库通常保留一份根目录笔记；真正复杂的多仓库工作区才考虑“简短恢复摘要 + 一份详细权威记录”，而且必须说明两者谁同步谁。
- **写入前核实现状** 对话历史只能当线索。分支、HEAD、工作区、PR、安装版本、备份和发布状态，都要从实际环境重新确认。
- **区分状态** `implemented`、`tested`、`human-validated`、`published`、`merged`、`installed`、`pending` 和 `superseded` 不能混着用。写完代码不等于测试通过，测试通过也不等于用户已经验收，更不等于已经上线。
- **只写有恢复价值的内容** 项目目标、不可违反的限制、当前工作流、根因、关键文件、测试结果、回滚点和下一步值得保留；每条命令、每段日志和临时猜测不值得。
- **只在有意义的节点更新** 确认根因、改变方案、完成测试、用户验收、发布、发生安全事故或准备交接时更新，而不是每动一下文件就记流水账。
- **保留历史，但不能让历史冒充现在** 失败方案可以留下，前提是明确标成 `superseded`、`obsolete` 或 `do not use`。如果某次操作造成数据丢失、降级、安装损坏或资源爆炸，还要把防止复发的规则写进去。
- **结束前审计** 检查路径、提交号、版本、PR 状态和下一步是否仍然准确；未完成的人工验收不能写成已通过；密钥、Token、Cookie 和私人提示词不能进入笔记。
- **笔记不自动获得发布权限** Skill 可以维护文件，但不能因为“这是开发笔记”就擅自提交或推送，除非用户已经授权，或者这份笔记本来就是当前补丁的一部分。

### note-schema.md：开发笔记最终写成什么样

Skill 决定要记以后，会参考 `references/note-schema.md`。它明确说这是一份菜单，不是要求每个项目都填满的表格。里面按恢复任务时最需要信息的顺序，列了九部分：

1. **笔记职责** 先写它负责哪个项目，是唯一权威记录、详细记录还是快速恢复摘要；有多份笔记时说明同步方向。
2. **不可违反的限制** 用户文件、备份要求、资源限制、网络环境、编码、安全和发布权限都放这里
3. **当前权威快照** 工作区路径、分支、HEAD、脏状态、PR、安装版本、Release、依赖版本等放在靠前位置，并持续原地更新。
4. **当前工作流与边界** 每项任务写目标、影响范围、明确排除项、依赖、关键文件、状态和下一道验证门槛
5. **重要工程结论** 按日期记录症状、已验证根因、采用的修复、关键代码位置、兼容边界、测试和剩余不确定性。
6. **测试与验收记录** 静态检查、局部测试、完整构建、CI、人工验收和真实安装验证分开写，不能拿其中一项代替其他项。
7. **安装、备份与回滚** 只有真正改动本机或线上产物时才写，包括替换了什么、没替换什么、备份在哪、如何验证和怎样回滚。
8. **废弃方案与事故** 保存那些能防止下一位 Agent 重踩的失败经历，并明确写出 `do not use`、`do not install` 或“仅供历史参考”。
9. **下一步** 只保留短而有顺序的待办；做完以后就移出这一节，把结果归入当前快照或工程历史

Schema 最后还限制了写法：跟随已有笔记的语言，标题尽量稳定，路径和提交号要精确，结论和证据优先于时间流水账，更不能把整段聊天记录原封不动贴进去。

### openai.yaml：让 Codex 知道这个 Skill 存在

`agents/openai.yaml` 内容很短，但它负责最后的接线：

- `display_name` 决定界面里显示“维护开发笔记”
- `short_description` 用一句话说明它适合复杂、多分支项目
- `default_prompt` 告诉 Codex 调用 Skill 时先评估项目，再维护准确的开发笔记。
- `allow_implicit_invocation: true` 允许 Agent 在满足条件时主动调用，而不要求用户每次都手写 `$maintain-development-notes`。

到这里，四个最终使用文件才算真正串起来：`AGENTS.md` 规定复杂任务要考虑开发笔记，`SKILL.md` 判断是否真的需要，`note-schema.md` 约束笔记内容，`openai.yaml` 负责让 Codex 能发现并自动调用它。

仓库里的完整文件放在这里：[Yuimi-chaya/codex-development-guidelines](https://github.com/Yuimi-chaya/codex-development-guidelines)。

## 不要每次都等客户端被动压缩

长会话迟早会碰到上下文窗口限制

很多人会一直聊，直到 Codex App 自己触发被动压缩。能用是能用，但压缩发生的时间不一定合适。

比如我刚解决完一个复杂问题，交付时已经使用了大约 60% 的上下文。接下来准备开启另一个同项目的大任务，而客户端可能在接近 80% 时才开始被动压缩。这时候如果直接把新 Prompt 发出去，很可能做到一半才压缩，刚加入的新需求、旧问题的收尾和工具输出全挤在一起。

我的做法是：趁上一件事刚完成、状态最清楚的时候，先确认开发笔记已经更新，再输入 `/compact` 主动压缩当前会话，然后开始下一项任务。Codex 本身也会自动压缩，但手动执行的好处是可以自己挑任务边界。

具体百分比并不是 OpenAI 保证不变的固定阈值，不同版本和模型也可能不一样。重点不是卡着 60% 或 80% 算命，而是把压缩放在**任务边界**，不要等它在任务中间突然发生。

主动压缩前可以让 Agent 先做一份很短的交接摘要：

- 刚完成了什么
- 修改了哪些文件
- 哪些验证已经通过
- 当前还有什么风险
- 下一轮从哪里开始

等这些信息已经写进开发笔记，再压缩会踏实很多

## 图片可能才是线程变胖的真正原因

这是一个比较离谱的地方

在我使用的客户端版本和实际线程文件里，工具返回的媒体内容可能以 Base64 形式进入线程记录。图片看起来只在对话里出现了一次，背后却可能是一大段文本数据。即使后面的任务已经完全用不到它，这段内容仍然跟着线程走。

如果一个会话里反复截图、读图、让工具返回处理后的图片，线程文件会膨胀得非常夸张。上下文压缩能总结文字，却不一定会替你把所有历史媒体负担处理干净。

我处理过的一个长会话，在备份并清理不再需要的 Base64 媒体数据以后，文件体积缩到了原来的大约五分之一。

但这里必须提醒一句：**这不是官方公开保证的稳定维护接口** 客户端内部结构可能随版本变化，别拿搜索替换直接扫文件，更不要在没有备份时修改正在使用的线程。

我自己的做法是把线程 ID 发给一个单独的维护会话，让它先定位、备份、检查格式，再清理确认已经不需要的媒体载荷。主任务线程不承担这类脏活，避免一边给自己减肥，一边又把扫描结果全部塞回上下文。

更省事的办法是从源头约束。我会在 `AGENTS.md` 里写清楚：凡是媒体文件接收、图片查找和素材路径确认，优先交给只读子代理；子代理只向主线程返回结论和文件路径，不要把图片本体再次返回到主线程。

这样不能解决所有问题，但至少不会每看一张图就给主会话背上一份 Base64 行李

## 别把客户端 Bug 当成模型变笨了

Codex App 出问题时，很容易第一反应是“GPT 怎么突然不会了”

但真实情况可能是页面脚本没重新绑定、插件刚安装还没刷新、当前线程拿到的工具定义已经过期、工作目录不对、客户端状态没有恢复，或者某个功能被门控挡住了。

我一般会先分层判断：

1. 文件有没有真的写到磁盘
2. 命令有没有在正确目录执行
3. 工具调用是否成功返回
4. 页面显示的是新状态还是旧缓存
5. 新线程或重启客户端后是否恢复
6. 最后再怀疑模型理解错了

尤其是涉及插件、工具和权限的改动，旧线程不一定会自动获得新的能力定义。有时重启客户端或新开线程不是玄学，而是让它重新加载环境。

## 最后还是得自己管项目

Codex App 最容易给人的错觉，是它已经能自己读代码、自己改、自己测试，所以用户只需要等结果。

短任务或许可以。长项目不行

你仍然要决定线程怎么拆、目录放在哪里、哪些信息应该进入长期规则、什么时候压缩、哪些素材不能碰、哪个版本值得保留，以及什么结果才算真的修好。

开发笔记、`AGENTS.md`、Git 提交和子代理分工，看起来都没有“让 AI 一句话生成项目”那么酷，但它们才是让长线程不失控的东西。

Codex App 的功能上限确实很高，产品完成度则经常让我血压也一起升高

既然短时间内改变不了客户端，那至少可以先把自己的目录、线程和上下文管明白。这样下次它再冒出什么奇怪设计时，我们面对的就只是一个产品 Bug，而不是一整个已经没人说得清的项目现场。
