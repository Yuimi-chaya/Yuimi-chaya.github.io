先直说，不绕弯子。

Codex App 的功能确实很前沿。它能直接读项目、改代码、开浏览器、跑测试、控制桌面应用，还能调用子代理处理任务。放在几年前，这些东西多少有点科幻。

但是，作为 OpenAI 这种大厂推出的官方编程工具，它现在还是有点拉跨。

Bug 满天飞、性能优化不怎么样、偶尔会出现反人类的交互设计，还有一些很奇怪的门控小巧思。最近越来越多 ChatGPT 相关能力也在往同一个产品壳里塞，我能理解他们想把功能做完整，但实际使用起来的体感就是越来越臃肿。有时候新功能还没来得及高兴，先得研究为什么我的按钮不见了、权限被挡了，或者同一个能力为什么在另一个入口里才能用。

当然，我一边骂还是一边在用。

因为只看“能帮我把项目做到什么程度”，Codex App 目前确实很强。只是想把它用得舒服一点，不能完全顺着客户端的默认设计走。下面这些经验不是官方标准答案，而是我在长时间会话、多任务项目和几次上下文事故以后慢慢留下来的习惯。

本文记录的是我在 **2026 年 7 月 27 日** 所使用版本中的体验。Codex App 更新很快，具体按钮、门控和内部文件格式以后都可能变化。

## 先给线程找个正经工作目录

如果一个线程只是临时问两句话，默认目录倒也无所谓。

但只要这个线程准备长期使用，或者需要生成代码、图片、文档、测试产物，我都建议先创建一个单独文件夹，再把它设为自定义工作目录。

不要什么都让它往类似下面这种默认位置里拉：

```text
C:\Users\你的用户名\Documents\Codex
```

刚开始看不出问题。等你积累了一堆项目副本、临时素材、预览产物、依赖目录和不知道属于哪个会话的文件，再碰上一次清理 C 盘，你就可以慢慢享受了。

我的习惯是一个长期项目对应一个明确目录，例如：

```text
D:\Projects\个人博客
D:\Projects\AstrBot插件
D:\Writing\论文项目
```

目录名字不重要，重要的是人能看懂、能备份、能进 Git，也知道删东西时自己删的是什么。

工作目录还会影响 Codex 能看到哪些文件、命令默认在哪里执行，以及项目里的 `AGENTS.md` 会不会生效。线程从一开始就站对地方，后面能省下很多解释。

## 一个线程最好只聊一类事情

不要在同一个线程里上午写论文，下午改博客，晚上再让它帮你写情书。

GPT 的抗干扰和长上下文能力已经很强了，但上下文被不同任务反复污染以后，它也遭不住。前一个任务的术语、格式要求、代码路径和语气偏好，都有可能在后面的回答里偷偷冒出来。

最简单的判断方式是：这些内容是否共享同一批文件、同一套背景和同一个最终目标？

如果答案是否定的，就新开线程。

同一个项目内部可以继续聊。例如博客的首页、文章页、播放器和部署，本来就会互相影响，放在一个长期线程里有价值。但论文和博客即使都需要写 Markdown，也没有必要硬塞在一起。

线程不是越长越厉害。能持续继承有效背景才有意义，只继承噪声就不是什么优点了。

## 长线程一定要让 Agent 写开发笔记

同一个项目里如果存在长会话、多任务分支、反复返工，或者需要跨很多天继续，我会直接要求 Agent 在仓库里维护一份 `DEVELOPMENT_NOTES.md`。

开发笔记不是聊天记录备份，也不是把每次命令输出全贴进去。那样只会再造一份上下文垃圾。

一份好用的开发笔记，应该优先写这些：

- 当前项目状态，以及现在真正生效的实现。
- 正在进行的任务和还没处理的问题。
- 关键文件、模块、函数、资源路径和提交号。
- 已经确认的根因，不要只写“这里有 Bug”。
- 试过但失败的方案，以及为什么不要再试。
- 可以回滚的 Git 提交点。
- 已经跑过哪些测试，哪些只是代码检查，哪些经过了人工验收。
- 下一步应该从哪里继续。
- 不能碰的用户素材、隐私内容和未跟踪文件。

我自己的博客开发笔记里，甚至会明确记录“这一版黑白十字能用”“某个空间扭曲方案已被否决”“细微视觉问题不要相信浏览器截图，要让我本人判断”。

这些信息看起来很琐碎，但经过几轮上下文压缩以后，它们比一段模糊的模型记忆可靠得多。

开发笔记最好把**当前状态放在最前面**，历史过程放后面。每次确认根因、完成一轮功能、切换任务或者准备交接时再更新，不要每执行一条命令就记一行。

还有两点很重要：不要把 Token、密码、Cookie 和密钥写进去；已经被推翻的方案要标记为“废弃”或“不要恢复”，不能让旧结论继续伪装成当前状态。

开发笔记的价值不只是防失忆。稳定、重复的项目背景被整理到固定文件里，也比每次临时重新讲一大段历史更容易复用上下文和缓存。至少不用让模型一轮轮重新猜“我们上次做到哪了”。

## 不要每次都等客户端被动压缩

长会话迟早会碰到上下文窗口限制。

很多人会一直聊，直到 Codex App 自己触发被动压缩。能用是能用，但压缩发生的时间不一定合适。

比如我刚解决完一个复杂问题，交付时已经使用了大约 60% 的上下文。接下来准备开启另一个同项目的大任务，而客户端可能在接近 80% 时才开始被动压缩。这时候如果直接把新 Prompt 发出去，很可能做到一半才压缩，刚加入的新需求、旧问题的收尾和工具输出全挤在一起。

我的做法是：趁上一件事刚完成、状态最清楚的时候，先确认开发笔记已经更新，再输入 `/compact` 主动压缩当前会话，然后开始下一项任务。Codex 本身也会自动压缩，但手动执行的好处是可以自己挑任务边界。

具体百分比并不是 OpenAI 保证不变的固定阈值，不同版本和模型也可能不一样。重点不是卡着 60% 或 80% 算命，而是把压缩放在**任务边界**，不要等它在任务中间突然发生。

主动压缩前可以让 Agent 先做一份很短的交接摘要：

- 刚完成了什么。
- 修改了哪些文件。
- 哪些验证已经通过。
- 当前还有什么风险。
- 下一轮从哪里开始。

等这些信息已经写进开发笔记，再压缩会踏实很多。

## 图片可能才是线程变胖的真正原因

这是一个比较离谱的地方。

在我使用的客户端版本和实际线程文件里，工具返回的媒体内容可能以 Base64 形式进入线程记录。图片看起来只在对话里出现了一次，背后却可能是一大段文本数据。即使后面的任务已经完全用不到它，这段内容仍然跟着线程走。

如果一个会话里反复截图、读图、让工具返回处理后的图片，线程文件会膨胀得非常夸张。上下文压缩能总结文字，却不一定会替你把所有历史媒体负担处理干净。

我处理过的一个长会话，在备份并清理不再需要的 Base64 媒体数据以后，文件体积缩到了原来的大约五分之一。

但这里必须提醒一句：**这不是官方公开保证的稳定维护接口。** 客户端内部结构可能随版本变化，别拿搜索替换直接扫文件，更不要在没有备份时修改正在使用的线程。

我自己的做法是把线程 ID 发给一个单独的维护会话，让它先定位、备份、检查格式，再清理确认已经不需要的媒体载荷。主任务线程不承担这类脏活，避免一边给自己减肥，一边又把扫描结果全部塞回上下文。

更省事的办法是从源头约束。我会在 `AGENTS.md` 里写清楚：凡是媒体文件接收、图片查找和素材路径确认，优先交给只读子代理；子代理只向主线程返回结论和文件路径，不要把图片本体再次返回到主线程。

这样不能解决所有问题，但至少不会每看一张图就给主会话背上一份 Base64 行李。

## AGENTS.md 是给 Agent 看的项目说明书

`AGENTS.md` 可以理解为仓库里的长期规则文件。

官方支持按目录层级读取它：项目根目录的规则影响整个仓库，更深目录里的 `AGENTS.md` 可以对局部模块追加或覆盖要求，离当前文件更近的规则优先。它很适合放那些每次开新线程都不想重新解释的内容。

不想从空文件开始写，也可以在项目里输入 `/init`，让 Codex 先生成一份骨架，再根据自己的环境删改。需要注意的是，这类规则通常在一次运行开始时建立指令链；中途刚改完却发现当前任务没完全吃到新规则，可以在保存以后开启新任务或重新载入，而不是和旧上下文死磕。

但别把 `AGENTS.md` 写成人类文明百科。越长不一定越有效，应该优先放真正会改变 Agent 行为的规则。

我认为至少值得写下面几类内容。

### 终端环境

先告诉它这是 Windows、PowerShell 还是 Git Bash。

PowerShell 不能当 Bash 用。路径里有中文、空格和括号时要加引号；命令失败后先分析原因，不能把同一条错误命令连续执行三遍；下载失败时优先怀疑网络环境，但不能擅自修改全局代理和镜像配置。

这种内容看起来基础，却能挡住大量无意义报错。

### 文件与编码

中文项目里一定要提醒编码问题。

看到乱码不能直接判断文件损坏，更不能自作主张把整份文件转成 UTF-8。修改已有文件时应尽量保留原编码、换行和结构；新文件再默认使用 UTF-8 without BOM。

还要明确最小修改原则：只改当前任务相关内容，不顺手格式化整个仓库，不删除用户文件，不覆盖来源不明确的图片。

### Git 与回滚

我会要求每轮有风险的改动前先留 Git 回滚点，只提交本轮相关文件，不要把用户未跟踪素材顺手一起提交。

同时禁止默认使用 `git reset --hard`、`git checkout --` 之类会直接抹掉工作区内容的命令。AI 改代码速度很快，毁掉未提交内容的速度也一样快。

### 构建与性能

禁止同时跑多个重型构建、测试、依赖安装和代码索引。长命令结束以后确认子进程是否真的退出，不要留下几个开发服务器一起吃内存。

这条是我真踩过的。工具层显示任务结束，不代表它启动的 Astro、Node 或其他后台进程也一定跟着退了。

我还会在 `AGENTS.md` 里明确规定：一旦我已经反馈电脑卡顿、CPU 拉满或磁盘狂转，Agent 就必须停止新增重型任务，先检查并收束现有进程，不能继续用“再跑一次完整构建看看”给机器加压。

### 子代理边界

查路径、找文件、数行数这种简单只读任务，可以交给轻量代理；中等难度的日志整理和代码追踪交给更强一点的代理；真正复杂的架构、疑难 Bug 和安全问题再用高推理模型。

每个子代理一次只做一个小任务，返回短摘要、证据和路径，不要返回大段日志，也不要继续创建它自己的子代理。完成后及时关闭，别让后台挂着一排不知道在干什么的线程。

### 验收方式

还要告诉 Agent 什么叫“完成”。

代码能编译不等于视觉效果正确，浏览器截图也不能代替真人判断细小动画手感。哪些任务必须跑测试，哪些要构建，哪些需要实际浏览器复现，哪些最终由用户目视验收，都可以写清楚。

下面是一份非常压缩的示意，不需要照抄：

```md
# Environment
- Windows + PowerShell，所有路径加引号。
- 禁止使用 Bash 专属命令；失败后先分析再换等价写法。

# File Safety
- 保留已有文件编码、换行和中文内容。
- 只做任务相关的最小修改，不覆盖来源不明的素材。

# Workflow
- 风险改动前创建 Git 回滚点。
- 重型构建和测试顺序执行，结束后检查残留进程。
- 多任务长会话维护 DEVELOPMENT_NOTES.md。

# Delegation
- 简单只读查找交给轻量子代理，只返回结论和路径。
- 子代理不得继续拆子代理，完成后及时关闭。
- 媒体任务不要把 Base64 图片返回主线程。

# Verification
- 修改后运行与风险范围匹配的测试。
- 微小视觉差异交给用户判断，不以工具截图代替验收。
```

## 别把客户端 Bug 当成模型变笨了

Codex App 出问题时，很容易第一反应是“GPT 怎么突然不会了”。

但真实情况可能是页面脚本没重新绑定、插件刚安装还没刷新、当前线程拿到的工具定义已经过期、工作目录不对、客户端状态没有恢复，或者某个功能被门控挡住了。

我一般会先分层判断：

1. 文件有没有真的写到磁盘。
2. 命令有没有在正确目录执行。
3. 工具调用是否成功返回。
4. 页面显示的是新状态还是旧缓存。
5. 新线程或重启客户端后是否恢复。
6. 最后再怀疑模型理解错了。

尤其是涉及插件、工具和权限的改动，旧线程不一定会自动获得新的能力定义。有时重启客户端或新开线程不是玄学，而是让它重新加载环境。

## 最后还是得自己管项目

Codex App 最容易给人的错觉，是它已经能自己读代码、自己改、自己测试，所以用户只需要等结果。

短任务或许可以。长项目不行。

你仍然要决定线程怎么拆、目录放在哪里、哪些信息应该进入长期规则、什么时候压缩、哪些素材不能碰、哪个版本值得保留，以及什么结果才算真的修好。

开发笔记、`AGENTS.md`、Git 提交和子代理分工，看起来都没有“让 AI 一句话生成项目”那么酷，但它们才是让长线程不失控的东西。

Codex App 的功能上限确实很高，产品完成度则经常让我血压也一起升高。

既然短时间内改变不了客户端，那至少可以先把自己的目录、线程和上下文管明白。这样下次它再冒出什么奇怪设计时，我们面对的就只是一个产品 Bug，而不是一整个已经没人说得清的项目现场。
