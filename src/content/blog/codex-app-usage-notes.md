先直说,不绕弯子

Codex App 的功能确实很前沿.它能直接读项目、改代码、跑测试、控制桌面应用,也能调用子代理处理任务.放在几年前,这些东西多少有点科幻.

但是,作为 OpenAI 这种大厂推出的官方编程工具,它现在还是有点拉跨

Bug 满天飞、性能优化不怎么样、偶尔会出现反人类的交互设计,还有一些很奇怪的门控小巧思.最近越来越多 ChatGPT 相关能力也在往同一个产品壳里塞,我能理解他们想把功能做完整,但实际使用起来的体感就是越来越臃肿.有时候新功能还没来得及高兴,先得研究为什么我的按钮不见了、权限被挡了,或者同一个能力为什么在另一个入口里才能用.

当然,我一边骂还是一边在用

因为只看“能帮我把项目做到什么程度”,Codex App 目前确实很强.只是想把它用得舒服一点,不能完全顺着客户端的默认设计走.下面这些经验不是官方标准答案,而是我在长时间会话、多任务项目和几次上下文事故以后慢慢留下来的习惯.

本文基于 **2026 年 8 月 10 日** 的使用体验整理.Codex App 更新很快,具体按钮、门控和内部文件格式以后都可能变化.

## 先给线程找个正经工作目录

如果一个线程只是临时问两句话,默认目录倒也无所谓

但只要这个线程准备长期使用,或者需要生成代码、图片、文档、测试产物,我都建议先创建一个单独文件夹,再把它设为自定义工作目录

~~不要什么都让它往类似下面这种默认位置里拉💩：~~

```text
C:\Users\你的用户名\Documents\Codex
```

刚开始看不出问题.等你积累了一堆项目副本、临时素材、预览产物、依赖目录和不知道属于哪个会话的文件,再碰上一次清理 C 盘,你就可以慢慢享受了.

我的习惯是一个长期项目对应一个明确目录,例如：

```text
D:\Projects\个人博客
D:\Projects\AstrBot插件
D:\Writing\论文项目
```

目录名字不重要,重要的是人能看懂、能备份、能进 Git,也知道删东西时自己删的是什么

工作目录还会影响 Codex 能看到哪些文件、命令默认在哪里执行,以及项目里的 `AGENTS.md` 会不会生效.线程从一开始就站对地方,后面能省下很多解释.

## 一个线程最好只聊一类事情

不要在同一个线程里上午写论文,下午改博客,晚上再让它帮你写情书

GPT 的抗干扰和长上下文能力已经很强了,但上下文被不同任务反复污染以后,它也遭不住.前一个任务的术语、格式要求、代码路径和语气偏好,都有可能在后面的回答里偷偷冒出来.

最简单的判断方式是：这些内容是否共享同一批文件、同一套背景和同一个最终目标？

如果答案是否定的,就新开线程

同一个项目内部可以继续聊.例如博客的首页、文章页、播放器和部署,本来就会互相影响,放在一个长期线程里有价值.但论文和博客即使都需要写 Markdown,也没有必要硬塞在一起.

线程不是越长越厉害.能持续继承有效背景才有意义,只继承噪声就不是什么优点了

## 长项目不能只靠聊天记录

一个长期任务不能只靠聊天记录维持.聊到几百轮以后,哪些文件不能碰、哪个方案已经试过、当前分支有没有推送,这些东西全靠模型从历史里猜,迟早会出事.

所以我后来把自己的长期规则和开发笔记方案整理成了一个叫 `codex-development-guidelines` 的仓库,链接放在这一节最后.它现在不再把参考 `AGENTS.md` 当作一份可以直接覆盖进用户目录的模板,而是要求先走采用或更新流程,把环境、终端、资源和能力路由这些真正会影响人的决定逐项讨论清楚.

检测到 Windows,不等于可以替用户决定只用 PowerShell.看见一条新规则,也不等于可以把已有 `AGENTS.md` 覆盖掉.先比较语义、处理冲突、展示最终 diff,再由人决定是否写入,这个步骤看着慢一点,却比以后花半天从错误的全局设置和误删文件里往回爬轻松得多.

完整参考文件放在这里：[Yuimi-chaya/codex-development-guidelines](https://github.com/Yuimi-chaya/codex-development-guidelines)

### 开发笔记最重要的不是写,而是四步循环

开发笔记的重点不要只放在“写下来”.

笔记如果从来不在开工前读,最后就只是一个看起来很认真的日志仓库.真正有用的开发笔记是一轮一轮地跑下面这个循环：**读 → 验 → 做 → 回写**

#### 第一步：读,先把已经知道的事情找回来

每次进入项目任务,在诊断、计划、写入和测试以前,SKILL会让模型先读最近的 `AGENTS.md`,再读已有的 `DEVELOPMENT_NOTES.md`、`HANDOFF.md` 或同等权威的记录.

这一读至少要找回六类东西：以前是否遇过同类问题,用户有哪些不能碰的偏好,哪些方案已经失败或被否决,项目的大方向是什么,上次真正验证过的状态是什么,还有哪些风险和人工验收仍然没完成.

开发笔记不是让模型比 Git 更相信旧文本,它只是把下一次调查的起点抬高一点,避免每次都像第一次打开项目一样乱猜.

#### 第二步：验,把笔记和现实重新对上

从笔记中读到的信息只能当线索,不能直接当事实

开工时先确认当前 Shell、工作目录和这次任务到底要改什么.如果是 Git 仓库,再看 `git status --short`、当前分支和 HEAD,这样就能弄清楚哪些改动是用户已经留在这里的,哪些文件绝对不能碰.

分支、提交号、工作树角色、测试结果、发布状态、备份和安装版本都一样.笔记里写着“已完成”,磁盘和远端却显示另一回事时,应该以重新查到的证据为准,再把笔记改正,而不是硬把现实往旧结论上解释.

#### 第三步：做,把范围、恢复点和验证一起带上

确认目标以后再动手,修改收在明确的文件和行为边界里.中文乱码不等于文件损坏,旧文件的编码、换行和结构不要为了“整齐”就重写,拥有中文的文件经常会出现终端中的编码显示问题；要让模型知道自己正在用的终端是什么,经常会出现不提的情况下全部默认为Bash.命令失败先看原因,换成当前环境真正可用的等价做法,而不是对着同一个错误连续重跑.

Git 项目还要有恢复点.要改已经验收的功能、视觉或媒体、状态机、全局配置和多文件逻辑,或者准备开始第二轮返工以前,先确认能回去的提交或任务级补丁.稳定后优先只提交本任务文件；工作区还有无关改动、暂时又不能提交时,就在仓库外留一份 `git diff --binary` 补丁或等价原样备份.未跟踪的素材和别人的修改不混进检查点,也不要为了图省事对整个工作区 `stash`,更不要拿 `reset --hard` 这种东西赌记忆.

测试也要把自动检查、完整构建、人工验收和发布状态分开说.代码写完不等于测试通过,测试通过不等于用户已经看过,用户看过也不等于它已经上线.

从 Shell、编码到图片和未跟踪文件,很多看起来琐碎的限制也都应该在这一步生效.路径加引号,下载失败只为当前命令临时处理,不改全局 npm、pip、Git、代理或默认 Shell；删除、覆盖、批量转码、全局配置、编码不确定和主观视觉判断先问.原图留在本地,审查用的图片控制在最长边 2048px、优先 WebP/JPEG 质量 80 到 85、单批不超过 12MB,透明和像素细节则用无损副本或局部裁切,也不要把高分辨率原图、完整 DOM、长日志和 Base64 一股脑塞进主线程.

#### 第四步：回写,只把下一次恢复真正需要的事实留下

确认根因、改了方案、跑完测试、完成真人验收、做了备份或回滚、建立提交、推送或发布以后,及时更新权威笔记.写的是已经核实的结论、证据、关键文件、准确提交号、剩余风险和下一步,不是把整段对话、完整日志和临时猜测再复制一遍.

状态也不能混用.`implemented`、`tested`、`human-validated`、`published`、`merged`、`installed`、`pending` 和 `superseded` 分开写,失败方案保留时明确标成历史或 `do not use`,这样下一位 Agent 才不会把“以前试过但失败”误读成“当前推荐”.密钥、Token、Cookie 和私人提示词当然更不该进笔记.

小到一次明确的单文件修改,不需要为了仪式感新建一本笔记.可一旦项目有多条工作流、分支或工作树、安装与回滚、长期调查、反复切换和快要压缩的上下文,读笔记与回写就不该省.

这四步连起来以后,开发笔记才不是单向的备忘录.它在开工时阻止重复调查,在执行中阻止误碰现场,在结束时把新证据交给下一轮恢复.

## 子代理不是按任务描述长短来分

“不要为了使用子代理而使用子代理”这句话本身没有问题,真正的问题是很容易把它理解成：只要任务描述不长,主线程就该自己两步做完.

这里说的主线程,就是当前正在和用户对话、负责最终判断的那条主任务.它最常见的误判是先觉得事情很简单,随后却一声不吭地扫目录、读长文件、翻大量日志,发现问题比想象中复杂以后还是继续独自埋头苦干.任务复杂不复杂,从来不是看 Prompt 有多少字,而是看它会不会跨很多文件和模块、会不会牵扯状态与验证、要不要消化大量上下文.

因此,主线程最多只做一次有限预检.只要任务跨两个以上模块或三个以上文件、需要读长文件或大量检索、涉及异步生命周期、状态机或竞态、碰到浏览器、视觉和媒体、根因不明、已经返工,或者一两步以后还没定位,就该先把已经确认的事实和剩下的疑点说清楚,再拆出一个边界明确的小任务交给子代理.

这并不等于所有小事都要分派.修改位置和方案都清楚、确实一两步能完成的工作,主线程直接做更快.需要避免的,是把最初那个“看起来简单”的判断无限延长.

这套分工里,三层的相对关系很简单：

| 层级      | 价格  | 速率  | 判断能力与适合的工作                            |
| ------- | --- | --- | ------------------------------------- |
| `luna`  | 最低  | 最高  | 吞吐、定位、长文件和日志压缩、资源整理、浏览器、明确授权的低风险小范围写入 |
| `terra` | 居中  | 居中  | 中等难度方案比较、实现审查、明确 Bug 分析,以及边界独立的中等实现   |
| `sol`   | 最高  | 最低  | 架构判断、复杂竞态、安全风险和独立反方意见                 |

也就是价格 `luna < terra < sol`,速率 `luna > terra > sol`,判断能力 `luna < terra < sol`.

`sol max` 适合留在主线程,负责理解需求、定边界、判断风险、审查结果、做最后验证和提交.交给 `luna` 的任务说明要写清输入、目标、允许写哪里、不能碰什么、返回什么、做到哪里停止.探索默认只读,同一个文件同一时间只能有一个写入者,第一次交付不合格最多再做一次有证据的定向返工,仍然不行就收回主线程.至少在模型能力层面上有原始分级的,`luna`能力外的事情,你让`sol`压力它几十次它也憋不出来真东西.为了保证效率,这时应该直接让主线程接手,而不是看着`sol`在那一直一句一句的教`luna`.

### 浏览器工具不要放在主线程

这一条可以说得很明确：无论看起来只是点一下还是要完整回归,都不建议主线程自己调用浏览器工具

原因不是主线程不会点,而是 `sol max` 的首字和输出速度本来就慢.浏览器操作又不是一个命令完事,点击、等待、看状态、再点击,每一步都要经历一轮工具交互.把这些多轮动作留在主线程,延迟会一层层叠起来,最后最简单的页面检查也能被拖得很久.最重要的是,浏览器返回的图片截图,都是以`Base64`的形式返回线程的,进一步扩大线程文件及上下文体积,使主线程的输出响应速度越来越慢.

所以浏览器统一交给 `luna max` 更合适.主线程把 URL、视窗、操作步骤、预期状态和停止条件交代清楚,`luna` 负责点击、悬浮、滚动、刷新、切路由、读取控制台或保存关键截图.它每一步都快,用户也能更快看到每一步到底点了什么、页面实际变成了什么,不会卡在主线程漫长的工具往返里.

主线程没有因此失去控制权,它仍然决定要验证什么、哪些结果算通过、要不要继续下一步.涉及登录态、发布、删除、保存云端配置或其他外部副作用时,让 `luna` 停在执行前一步,主线程先判断风险并取得确认,再决定继续还是让用户亲自操作.

返回主线程的内容也应该很轻：截图路径、关键数值、实际结果和复现步骤就够了,不要回传一整页 DOM、连续截图和 Base64.浏览器截图适合看大范围布局、状态和明显回归,链节咬合、材质厚度、微小位移和整体手感这种细节,最后仍然留给用户人眼验收.

## 不要每次都等客户端被动压缩

很多人会一直聊,直到 Codex App 自己触发被动压缩.能用是能用,但压缩发生的时间不一定合适.

比如一个复杂问题刚交付时,已经使用了大约 60% 的上下文.接下来准备开启另一个同项目的大任务,而客户端可能在接近 80% 时才开始被动压缩.这时候如果直接把新 Prompt 发出去,很可能做到一半才压缩,刚加入的新需求、旧问题的收尾和工具输出全挤在一起,可能会造成一定的注意力损失,即丢失原 Prompt 中的目标导致最终交付不佳.

更稳妥的做法是：趁上一件事刚完成、状态最清楚的时候,确认这一轮已经走完开发笔记第四步的流程,直接 `/compact` 主动压缩当前会话,然后开始下一项任务.

具体的被动压缩百分比并不是 OpenAI 保证不变的固定阈值,不同版本和模型也可能不一样.重点不是卡着 60% 或 80% 算命,而是把压缩放在**任务边界**,不要等它在任务中间突然发生.而且按照  Codex 的工作流程来说,每次模型的调用都是会上传上次压缩后到现在的所有上下文,也就是说,合理的主动压缩也可以减轻token消耗.

## 图片可能才是线程变胖的真正原因

这是一个比较离谱的地方

Codex 客户端版本和实际线程文件里,工具返回的媒体内容通常会以 `Base64` 形式进入线程记录.图片看起来只在对话里出现了一次,背后却可能是一大段文本数据.即使后面的任务已经完全用不到它,这段内容仍然跟着线程走.

真正容易出事的不是只看一张普通截图,而是模型原样同时读取好几张高分辨率图片.几张 4K 原图、连续截图或图片处理后的中间结果一起进来,线程体积会很快暴涨；请求或工具载荷超过网关限制时,还可能直接撞上 `413 Payload Too Large` ,这时候就会直接拒绝你的请求导致这个线程中的模型请求不可用了.

上下文压缩能总结文字,但不会替你把所有历史媒体处理干净.我处理过的一个长会话,在备份并清理不再需要的 Base64 媒体数据以后,文件体积缩到了原来的大约五分之一.

处理方法为:新建一个空白线程,将需要被清理的线程id准备好,连同着id一并告诉它:

*"备份并清理id为XXXXX的线程文件中的Base64"*

但这里必须提醒一句：**这不是官方公开保证的稳定维护接口** ,只是社区中可信度较高的方法,至少我也试过,很有用.

更可靠的办法还是从源头控制.原图始终留在本地,让模型在正式读取前先检查像素尺寸和文件体积,需要送去审查时再生成压缩副本

工具回传的 Base64也不要让主线程硬吃.把图片查找、素材确认、截图和图片处理交给成本最低的 `luna`,让它承接工具返回的 Base64,最后只把真实图片路径、必要的尺寸或格式信息和一句结论返给主线程就行.这样主线程仍然知道该看哪张图、问题有没有定位,却不用把每一张图片的Base64永远存在线程文件中.

这不是为了把子代理硬塞进流程,而是把最容易膨胀的媒体载荷留在便宜又快的执行层.能在主线程直接确认的一张小图当然没必要专门分派,但一旦变成多张高分辨率图片、连续截图或工具链回传,先压缩、再让 `luna` 吞掉返回内容,通常比事后处理一条越来越胖的线程轻松得多.

## 别把客户端 Bug 当成模型变笨了

Codex App 出问题时,很容易第一反应是“GPT 怎么突然降智了”

但真实情况可能是页面脚本没重新绑定、插件刚安装还没刷新、当前线程拿到的工具定义已经过期、工作目录不对、客户端状态没有恢复,或者某个功能被门控挡住了

我一般会先分层判断：

1. 文件有没有真的写到磁盘
2. 命令有没有在正确目录执行
3. 工具调用是否成功返回
4. 页面显示的是新状态还是旧缓存
5. 新线程或重启客户端后是否恢复
6. 最后再怀疑模型理解错了

尤其是涉及插件、工具和权限的改动,旧线程不一定会自动获得新的能力定义.有时重启客户端或新开线程不是玄学,而是让它重新加载环境.SKILL以及插件的安装及更新,都是需要重启 App 的,通常不需要新开线程.

## 最后还是得自己管项目

Codex App 最容易给人的错觉,是它已经能自己读代码、自己改、自己测试,所以用户只需要等结果

短任务或许可以.长项目不行

你仍然要决定线程怎么拆、目录放在哪里、哪些信息应该进入长期规则、什么时候压缩、哪些素材不能碰、哪个版本值得保留,以及什么结果才算真的修好

开发笔记的四步循环、`AGENTS.md`、Git 检查点和子代理分工,看起来都没有“让 AI 一句话生成项目”那么酷,但它们才是让长线程不失控的东西

Codex App 的功能上限确实很高,产品完成度则经常让我血压也一起升高

既然短时间内改变不了客户端,那至少可以先把自己的目录、线程和上下文管明白.这样下次它再冒出什么奇怪设计时,我们面对的就只是一个产品 Bug,而不是一整个已经没人说得清的项目现场.
