开始用 AI 写项目以后,你很快就会发现 token 不是一个抽象的数字.它是一次又一次的读代码、改代码、失败重试,也是你刚要开始下一轮任务时突然看见"额度不足"的那个瞬间.

先说在前面,这篇文章不会推荐任何第三方中转站,也不会指着某一家官方的某个服务说"买它就对了".我想聊的是这些 token 究竟从哪里来,不同买法解决了什么问题,以及掏钱之前有哪些账不能只看宣传图.

## 官渠好懂,但不一定好买

走官方渠道通常就两条路:买一个有周期额度的订阅套餐,或者开 API 按实际用量付费.国内模型的购买入口和支付方式对不少人来说比较直接,选好适合自己的套餐或 API,照着平台说明开通就能用.换成 GPT、Claude、Grok 等海外服务,支付卡、身份或地区要求、网络连通性都可能成为门槛,每家的规则也不一样;这不是换个客户端就能解决的事.

很多时候,**只要你用得足够多,订阅摊下来确实比按官方 API 单价逐笔结算便宜.** 但它卖的是一段时间内可用的额度,不是往账户里存了一笔永远花不完的钱.你得留意到期日、周期额度、滚动窗口和触发限额后的恢复时间;用得少时怕浪费,用得多时又怕下一轮任务被限额挡住.那种明明付了钱,却总觉得有人轻轻揪着小辫子催自己赶紧用的感觉,我想不少人都懂.

API 的好处是按量算账,什么时候用、用多少都比较直观,但也别把"充值余额"自动理解成永久有效:有效期、退款和账户停用后的处理仍要看各家的条款.订阅与 API 也不是一笔账,例如 [Codex 官方的套餐说明](https://learn.chatgpt.com/docs/pricing)区分了订阅使用额度与 API Key 的按量计费,不能把两套规则拿来直接互换.

## 中转站填的是什么空

这就到了中转站出场的地方.你给中转站付款,拿到它提供的接口和密钥,由它去连接上游模型;对使用者而言,它可能同时解决支付、连通性和多模型接入的问题,还把一次性购买套餐变成了看起来可以慢慢花的站内余额.

其中有一种常见做法,是把订阅账号的使用能力转成供客户端调用的接口,再通过多个账号轮转来分摊请求与限额.只要有人持续使用、号池和成本能维持住,生意就能继续运转.**但中转站不全是这种模式**,也有使用上游正式 API、聚合不同供应商或混合多种渠道的;不能因为它叫"中转"就断定背后一定是订阅反代.反过来,页面写着"官方模型"也不能证明它真在走官方 API,更不能证明转售方式符合上游条款.例如 [Claude Code 的官方说明](https://code.claude.com/docs/en/legal-and-compliance)对第三方使用订阅凭证就设有明确边界,这类限制需要按具体服务分别看.

所谓"余额常驻"也只是相对订阅窗口的一种体验,不是你的钱从此有了保险箱.平台可以改规则,上游账号可能失效,站点也可能突然无法访问.所以我自己的原则很简单:**用多少充多少**,不要因为一个夸张的折扣就把未来半年的预算先压进去.

还有更不能忘的一笔账:请求经过中转站,你的提示词、代码片段、文件内容以及可能携带的凭证,就有机会被它接触.个人娱乐项目和公司的私有仓库,我会用完全不同的标准判断;前者也应避免发送密码和个人隐私,后者则不能只凭"这家群里人很多"就放行,还得看组织允许的数据路径和供应商约定.

当然,这不等于官方客户端就天然不会碰你的隐私.2026 年 9 月,有用户[公开了 ZCode 旧版本打包工作区并尝试上传的取证过程](https://blog.ferstar.org/en/posts/zcode-silent-workspace-snapshot-upload/):他发现的大型商业仓库快照停在本地,上传未成功,另一个小型测试仓库则出现了服务端接收记录.ZCode 在[更新记录](https://zcode.z.ai/_next/changelog)中写明修复了"仓库百科异常上传",研究者对后续版本的检查也没有再发现旧上传流程.他还质疑过事后公开的源码仓库关闭了 Issues 与 PR,让外界难以在那里继续追问;这属于事件处理方式的争议,不能替代对上传行为本身的取证.这个例子不是为了把所有官方产品和所有中转站画等号,而是提醒我自己:问清楚数据实际会经过哪里、会不会保存、能不能关闭,比单凭"官方"或"第三方"四个字判断更有用.历史数据是否彻底清除,也不能只靠一条更新说明替外部用户作保证.

## 买之前,先把数字翻译成人话

看中转的价格,第一步不是比较谁的"倍率"小,而是先问清楚 **1 元人民币能买多少站内余额,余额是什么单位,倍率又乘在哪个基准价上**.有的写"1 元=1 刀=1 余额,0.03 倍率",有的写"1 元=0.2 刀=0.2 余额,0.15 倍率".假设两家都以官方 API 价目表中同一笔 1 美元的用量为基准,A 家扣 0.03 余额,也就是约 0.03 元;B 家扣 0.15 余额,但 1 元只买到 0.2 余额,实际就是约 0.75 元.这两个例子只是演示算法,不是现实站点报价,而且不同模型、输入输出和缓存可能各有倍率.宣传页只甩一个"0.03"或"0.15",却不说单位和扣费公式,我就不会下单.

定价不一定非得追求最低,自己觉得值就行.真正容易吃亏的是,上游靠订阅额度摊薄了成本,站内却照着正式 API 原价甚至更高的价格向你收费,而你以为自己买的是同一回事.尤其是 Codex 相关模型,别见到"缓存创建费"或"长上下文翻倍"就理所当然接受:官方 [API 价目表](https://developers.openai.com/api/docs/pricing)确实对部分模型列出了长上下文和缓存写入价格,但 [Codex 订阅与额度说明](https://learn.chatgpt.com/docs/pricing)明确区分了 API Key 计费,并写明 Codex 的积分计费没有单独的缓存写入收费.订阅下长任务可能更快消耗额度,这和直接套用 API 的长上下文倍率、再逐项收你一笔"缓存创建费"不是一回事.问清楚它用的是什么上游、按什么规则计费,再决定价格是否合理.

价格看明白后,我还会先找售后入口:有没有明确的联系方式或频道,出错、扣费争议和退款要找谁.有群不代表不会跑路,没群也不能单凭这一点断定质量,关键是问题发生时能否找到人、能否拿到清楚的用量记录.先小额充值,在自己常用的时段试,比一次买一大包然后祈祷它稳定靠谱得多.

最后再看上游本身.用同一类任务测首字速度和后续流式输出,不要只测一次开头就宣布"秒回";重复发送有稳定前缀的请求,观察缓存是否真的按宣传命中,同时留意号池切换、模型路由和提示词变化可能带来的差异.想判断有没有掺水,可以用不联网的问答和一次成型的小作品与自己信得过的渠道做盲测,再对照实际响应中的模型信息.这些都只是筛查线索,**模型名、所谓"指纹"或一道题的表现,单独拿出来都不能证明上游身份**,也别把偶然一次发挥失常直接判成换模型.

## 最后才是接入 Codex

确认自己买的是什么之后,接入反而不是最难的一步.[CC Switch](https://github.com/farion1231/cc-switch)、[Codex++](https://github.com/BigPizzaV3/CodexPlusPlus)或者其他同类工具,都可以帮你管理供应商配置和切换入口.Codex++ 是我一直参与维护的项目,所以在这里提到它也算作利益相关说明,不把它伪装成一份中立排行榜.

实际配置时,先确认服务给的密钥和接口地址对应哪种协议、支持哪些模型与工具能力,再用小任务试通,核对一次真实扣费.一个地址能返回聊天文字,不代表它就完整支持 Codex 的工具调用、长任务和上下文处理;能接上,与适合长期拿来开发,中间还隔着稳定性、账单和数据边界.

说到底,流水的 token 没有一种对所有人都完美的买法.官方订阅省心或划算的前提是你能买到、用得上,按量 API 清楚但账单可能更高,中转改善了入口和余额体验,也把价格、上游和信任问题一并交到了你手里.别先问哪家倍率最低,先弄明白自己到底把代码交给了谁,又是在按哪一套规则付钱.
